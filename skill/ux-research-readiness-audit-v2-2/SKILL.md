# 用户研究就绪度审计 V2.2

## 目标

在用户研究基本完成、正式进入原型设计之前，审计现有研究是否已经形成足够、可追溯的设计依据。

本 Skill 主要面向初级 UX 设计师，重点防止：

- 只整理访谈内容，没有形成结构化分析；
- 用户痛点、需求和核心功能缺少证据；
- 将用户原话、功能建议或设计师猜测直接当成需求；
- 研究不足时过早进入原型，导致中途返回研究阶段并返工；
- 为了形式完整而机械制作用户画像、HMW 等产物；
- 使用 AI 自动补出不存在的用户事实或研究结论。

## 核心原则

1. **先审计证据，再审计分析产物。**
2. **检查核心问题是否被回答，不机械检查方法名称。**
3. **核心功能必须能追溯到用户问题、需求或明确约束。**
4. **证据充分但分析缺失时，可以生成分析初稿。**
5. **证据不足时，不得用生成内容掩盖研究缺口。**
6. **AI 提问、检查、整理和提出备选路径；设计师确认、修正和决策。**
7. **所有推断必须显式标记，不得伪装成事实。**
8. **审计结论必须附证据、问题编号、严重程度和复审条件。**
9. **审计只判断证据支持程度与进入原型的风险，不替设计师决定具体功能层级、流程归属或最终方案。**
10. **小样本可以支持探索、发现问题和形成假设，但不得被用来宣称普遍性、发生比例或长期效果。**
11. **先识别根因和冲突层级，再判断 Issue 严重度；九项最低分析包的状态不得自动一项生成一个 Issue。**
12. **暂停当前既定方案不等于暂停问题方向。证据支持问题存在、但不支持某个默认值或方案时，应继续多路径、低成本探索。**
13. **`BLOCKER` 必须通过反事实门槛：低成本、可逆、明确标注为假设的原型仍无法产生有效学习，或继续探索会造成不可逆风险时才可使用。**
14. **默认输出精简报告；只有用户明确要求、项目高风险或需要正式审计归档时才输出完整报告。**

## 使用阶段

适用于：

- 新产品概念在完成探索性研究后、进入原型前；
- 已有产品新增功能在完成需求研究后、进入原型前；
- 产品流程重构在完成现状研究后、进入原型前；
- 概念验证准备制作可测试原型之前；
- 设计师怀疑研究分析不完整、功能依据不清或即将发生返工时。

不适用于：

- 尚未开始任何用户研究，只想让 AI 直接定义需求；
- 已进入高保真阶段，仅需要界面可用性或视觉审计；
- 单纯进行竞品视觉分析；
- 需要验证已完成原型的可用性；
- 需要替团队做最终产品决策；
- 只想自动生成完整 UX 交付物而不提供研究证据。

## 项目模式

开始审计前，先确定项目模式：

- `NEW_PRODUCT`：新产品或新服务；
- `FEATURE_ADDITION`：已有产品新增功能；
- `FLOW_REDESIGN`：已有核心流程重构；
- `CONCEPT_TEST`：概念验证或快速探索；
- `RESEARCH_RECOVERY`：原型过程中发现研究不足，返回补做分析。

项目模式只影响审计深度和允许的未决项，不改变证据真实性要求。

详细规则见 [审计框架](references/audit-framework.md)。

## 所需输入

优先请求以下材料；允许用户分批提供：

1. 项目背景、业务目标和当前阶段；
2. 目标用户或预期用户；
3. 研究问题与研究范围；
4. 原始研究材料：访谈记录、观察记录、问卷原始结果、日志、行为数据、客服记录等；
5. 已有分析产物：编码、亲和图、洞察、画像、旅程图、任务分析、HMW、问题陈述等；
6. 当前定义的核心痛点、需求和优先级；
7. 已确定或计划中的核心功能与核心流程；
8. 已知业务、技术、时间或合规约束；
9. 计划通过原型验证的问题；
10. 设计师当前最担心的研究缺口。

不要把“没有提交某一种文档”直接视为缺失。先判断其他材料是否已经回答对应核心问题。

## 工作流程

### 0. 建立审计上下文

记录：

- 项目模式；
- 产品阶段；
- 目标用户；
- 核心任务；
- 可用时间；
- 材料完整度；
- 用户希望获得的结果：仅审计、审计并补齐分析初稿、或审计并制定研究计划。

材料过多时，先建立索引，不立即下结论。

### 1. 材料盘点与分类

将输入分成四类：

- `EVIDENCE`：可追溯的原始证据；
- `ANALYSIS`：基于证据形成的归纳、模式、洞察或模型；
- `DECISION`：产品目标、需求优先级、功能或流程决策；
- `ASSUMPTION`：尚未验证的推断、期待或方案假设。

每条材料分配唯一编号：

- 证据：`EV-001`
- 分析：`AN-001`
- 决策：`DE-001`
- 假设：`AS-001`

输出材料盘点表，并指出缺少的必要输入。

### 2. 建立证据索引

对核心结论建立可追溯关系：

`原始证据 → 研究模式 → 用户问题 → 用户需求 → 设计目标 → 功能或方案假设`

每条证据至少标记：

- 证据 ID；
- 文件路径或来源名称；
- 参与者、数据集或资料编号；
- 日期、版本或采集批次；
- 页码、段落、行号、题号、时间戳或记录位置；
- 原文摘录、行为观察或数据定义；
- 支持的结论；
- 适用范围、限制、反例与冲突；
- 匿名化状态；
- 置信度；
- 是否经过设计师确认。

若无法定位原始位置，不得将该条证据单独用于支持核心需求或核心功能。

详细规则见 [证据与严重度规则](references/evidence-and-severity.md)。

### 3. 审计九项最低分析包

必须检查：

1. 研究证据索引；
2. 用户与场景说明；
3. 核心痛点和需求；
4. 问题定义；
5. 用户任务或核心旅程；
6. 需求优先级；
7. 证据—功能对应关系；
8. 假设与风险清单；
9. 原型验证目标。

每项标记为：

- `SUFFICIENT`：核心问题已被充分回答；
- `PARTIAL`：存在轻度缺失，不影响核心判断；
- `MAJOR_GAP`：重要缺失，会影响研究质量或原型范围，但不一定阻断低成本探索；
- `BLOCKING_GAP`：核心链路断裂，继续相关核心原型会建立在不可接受的不确定性上；
- `NOT_APPLICABLE`：经解释后不适用。

不得只根据是否存在某个文档判断。使用 [审计框架](references/audit-framework.md) 中的核心问题与合格标准。

对“原型验证目标”必须额外拆分三个状态，避免把完整计划误写成已完成验证：

- `validation_plan_status`：`NOT_PLANNED` / `PARTIAL_PLAN` / `SUFFICIENT_PLAN`；
- `validation_execution_status`：`NOT_EXECUTED` / `IN_PROGRESS` / `EXECUTED_WITH_RECORDS`；
- `validation_evidence_status`：`NO_EVIDENCE_YET` / `PARTIAL_EVIDENCE` / `EVIDENCE_AVAILABLE`。

`SUFFICIENT_PLAN` 只说明计划完整，不代表已经产生验证证据。

### 4. 识别缺失原因

对每个缺口区分：

- `UNORGANIZED`：证据存在，但未整理；
- `UNDER_ANALYZED`：已有分析，但不足以回答核心问题；
- `EVIDENCE_MISSING`：缺少原始证据；
- `EVIDENCE_CONFLICT`：关键证据互相冲突；
- `SOLUTION_BIAS`：先有解决方案，再反向寻找依据；
- `SCOPE_AMBIGUITY`：研究范围或项目目标不清；
- `TRACEABILITY_BREAK`：证据链断裂；
- `UNTESTED_ASSUMPTION`：高风险假设未标记或未验证。

### 5. 识别冲突层级、根因并生成 Issue

#### 5.1 先判断冲突发生在哪一层

- `PROBLEM_EXISTENCE`：问题是否真实存在；
- `USER_OR_CONTEXT_SCOPE`：只对哪些用户、场景或任务成立；
- `NEED_TRADEOFF`：多个用户目标或代价之间存在张力；
- `SOLUTION_OR_DEFAULT`：具体方案、默认值、功能层级或流程选择存在冲突；
- `INTERACTION_DETAIL`：文案、入口、反馈或交互细节存在冲突。

只有 `PROBLEM_EXISTENCE` 层的关键冲突，或安全、伦理、隐私、合规等不可逆风险，才通常有资格进入 `BLOCKER` 判断。用户范围、需求权衡、方案与交互层冲突默认先收窄主张、分群或比较多种方案，不得直接阻断整个问题方向。

#### 5.2 建立根因注册表

先给每个独立根因分配：`RC-001`、`RC-002`……，至少记录：

- `root_cause_id`；
- 根因描述；
- 支持证据或缺失证据；
- `conflict_level`；
- 受影响的最低分析包维度 `affected_dimensions`；
- 当前阶段与项目模式；
- 可否通过低成本原型继续学习；
- 是否存在不可逆风险；
- 负责人、处理路径与复审条件。

九项最低分析包只用于定位受影响维度。**一项为 `MAJOR_GAP` 或 `BLOCKING_GAP`，不代表必须单独生成一个 Issue。** 同一根因影响多个维度时，默认只生成一个主要 Issue，并在 `affected_dimensions` 中列出影响范围。

只有当以下条件成立时才拆分为多个 Issue：

- 需要不同负责人；
- 需要不同处理方法；
- 风险级别不同；
- 复审条件不同；
- 分开处理会明显提高可执行性。

若生成超过 6 个未关闭的根因 Issue，必须先执行一次去重检查，说明为什么不能进一步合并。

#### 5.3 BLOCKER 反事实门槛

每个候选 `BLOCKER` 必须依次回答：

1. 核心用户、场景或问题存在性是否无法确定？
2. 一个低成本、可逆、明确标注为假设的原型，能否直接帮助解决该不确定性？
3. 继续探索是否会造成不可逆的安全、伦理、隐私、合规或重大业务风险？
4. 团队是否准备把该原型直接用于高成本实现、正式发布或“研究已证明”的对外主张？
5. 是否存在明确的学习目标、停止条件和复审点？

若第 2 项为“能”，第 3、4 项为“否”，且第 5 项为“有”，通常不得使用 `BLOCKER`；应使用 `MAJOR` 并输出 `EXPLORE_WITH_GUARDRAILS`。

#### 5.4 生成 Issue

Issue ID：`UXRA-{领域代码}-{三位序号}`。

领域代码：`EVI`、`USR`、`NEE`、`PRB`、`JNY`、`PRI`、`FTR`、`RSK`、`VAL`、`SCP`。

严重程度：

- `BLOCKER`：核心问题方向无法成立或无法通过安全、可逆探索产生有效学习；
- `MAJOR`：方向可能成立，但主张、范围、方案或重要证据链需要修正；
- `MINOR`：不影响当前核心决策，可后续完善。

每个 Issue 必须包含：

- `root_cause_id`；
- `affected_dimensions`；
- `conflict_level`；
- 问题与证据边界；
- 为什么重要；
- 对当前原型范围的影响；
- 建议处理方式；
- 预计成本；
- 复审条件。

#### Issue 注册表与统计一致性

Issue 列表是整份审计报告中 Issue 数据的**唯一事实来源**。不得在审计摘要、三档总评或审计记录中手工重新估算数量。

生成 Issue 后必须先建立注册表，至少包含：

- `issue_id`；
- `domain`；
- `severity`；
- `gap_status`（如适用）；
- `resolution_status`；
- `action_plan_required`；
- `review_condition`。

随后从该注册表派生：

- `blocker_count`；
- `major_count`；
- `minor_count`；
- `total_issue_count`。

这些派生值必须原样复用到审计摘要、三档总评、行动计划摘要和审计记录中。禁止在不同章节分别填写统计数字。

提交前必须检查：

1. Issue ID 唯一且格式有效；
2. `BLOCKER + MAJOR + MINOR = 总 Issue 数`；
3. 摘要、Issue 表、三档总评和审计记录中的统计完全一致；
4. 行动计划引用的每个 Issue ID 都存在于注册表；
5. 每个未关闭的 `BLOCKER` 和 `MAJOR` 都有行动项或明确的设计师确认点；
6. 不存在 Issue 表中有记录、但摘要漏计的项目；
7. 不存在摘要计入、但 Issue 表中不存在的项目。

若发现不一致，必须先修正统计和交叉引用，再输出最终报告。

### 6. 动态选择分析方法

先确定缺失内容要回答的核心问题，再选择方法。

选择顺序：

1. 能否直接从已有证据整理完成；
2. 是否有轻量方法可以回答；
3. 是否需要组合多个方法；
4. 是否必须补充研究；
5. 是否存在更低成本但同样有效的替代方案。

方法选择必须考虑：

- 缺口类型；
- 现有证据；
- 项目模式；
- 任务复杂度；
- 可用时间；
- 输出用途；
- 决策风险。

不得固定执行“缺少 X 就一定制作 Y”。

详细方法见 [分析方法库](references/method-library.md)。

### 7. 选择执行模式

#### 模式 A：仅推荐

适用于用户只需要审计意见。

输出：

- 推荐方法；
- 使用原因；
- 操作步骤；
- 所需输入；
- 预计耗时；
- 预期产出。

#### 模式 B：生成分析初稿

仅在证据足够且可追溯时使用。

要求：

- 每条分析引用证据编号；
- 明确区分事实、模式、洞察和推断；
- 标记置信度；
- 不扩展到证据没有覆盖的用户或场景；
- 在进入下一步前请求设计师确认。

#### 模式 C：补充研究计划

证据不足、冲突严重或样本无法支持核心结论时使用。

输出：

- 需要验证的问题；
- 推荐研究方法；
- 目标参与者；
- 最小可行样本或资料来源；
- 招募/执行重点；
- 预计时间；
- 完成后应更新的分析项。

不得生成虚假的洞察、画像或需求。

### 8. 人工确认门与设计决策边界

以下节点必须暂停并要求设计师确认：

1. 目标用户与项目范围；
2. 核心证据引用是否准确、完整且未改变原意；
3. AI 对证据的归纳是否符合原始语境；
4. 核心痛点、需求和方案是否被正确区分；
5. 核心需求优先级；
6. 证据—功能对应关系；
7. 高风险假设及其验证方式；
8. 是否继续探索性原型；
9. 是否可以对外将某项内容表述为“研究已支持”；
10. 最终产品与设计决策。

确认选项统一为：

- `确认`
- `部分确认并修改`
- `不确认`
- `需要更多证据`
- `保留为待验证假设`

若设计师不确认，不得把该项作为已验证结论。

#### 审计建议允许做什么

可以：

- 指出某个功能作为核心功能时证据不足；
- 说明不同功能层级选择分别需要什么证据；
- 提供两个或多个可选处理路径；
- 解释每条路径的研究风险、成本和验证目标；
- 要求设计师选择、修改或拒绝建议。

不可以：

- 直接规定某个功能必须成为核心、次级或被删除；
- 直接固定产品核心流程；
- 用“建议”措辞替代设计师做最终取舍；
- 用命令式方案句替代证据边界，例如“应当改为……”“必须使用……”；
- 因证据不足而声称相反方案已经成立；
- 把审计结论包装为产品决策结论。

当证据只能否定某个既定方案时，输出必须采用：

1. 当前证据不支持什么；
2. 当前证据仍支持什么；
3. 至少两个可选处理路径；
4. 每条路径的验证目标与风险；
5. `DESIGNER_DECISION_REQUIRED`。

不得把其中任一路径写成唯一正确答案。

当输出涉及功能层级、范围或流程调整时，必须使用：

`DESIGNER_DECISION_REQUIRED`

并至少给出：

- 当前证据支持什么；
- 当前证据不支持什么；
- 可选处理路径；
- 每条路径需要验证的内容；
- 设计师最终选择栏。

### 9. 停止规则

出现以下情况，停止自动补齐并转为补充研究或澄清：

- 没有任何真实用户证据，却要求生成用户洞察；
- 核心用户和场景无法确定；
- 核心问题仅来自设计师个人推测；
- 关键证据在“问题存在性”层互相冲突，且无法通过分群、收窄范围或低成本原型继续学习；
- 需要把个别用户观点推广到整体用户群；
- 输入要求编造访谈、数据、引用或参与者；
- 核心功能完全无法追溯到需求或约束；
- 用户要求 AI 替其做最终设计决策；
- 材料包含敏感信息但未进行必要匿名化。

停止时必须说明：

- 为什么停止；
- 当前仍可确定的内容；
- 缺少什么；
- 最低成本的补充路径；
- 何时可以重新审计。

### 10. 给出双维度结论与三档总评

不得仅根据 Issue 数量机械决定结论。必须判断两个核心维度，并单独记录方案收敛状态：

1. **是否允许继续原型探索**；
2. **当前既定方案是否可以继续收敛，还是只能作为假设或需要暂停**；
3. **是否可以把当前设计主张表述为已被研究支持**。

#### 维度 A：原型探索状态

##### `EXPLORE`

可以继续原型探索。

条件：

- 无 `BLOCKER`；
- 目标用户、核心场景和核心问题至少具有可追溯的中等置信度证据；
- 原型验证目标明确；
- 未决问题能够通过低成本原型或针对性研究继续学习；
- 原型不会被误当成最终已验证方案。

##### `EXPLORE_WITH_GUARDRAILS`

可以继续低成本、可逆的探索性原型，但必须带限制。

典型情况：

- 无 `BLOCKER`，但存在一个或多个与核心方向相关的 `MAJOR`；
- 核心方向有初步证据，但证据链、优先级或方案形态仍不完整；
- 每个关键 `MAJOR` 已有负责人、验证目标和复审条件。

限制：

- 不进入高成本精细化、开发承诺或结论性展示；
- 不把未验证功能写成已成立需求；
- 原型范围只覆盖需要学习的问题。

##### `PAUSE_CORE_PROTOTYPING`

暂停整个问题方向的核心原型工作，而不仅是暂停某个既定方案。

通常需要通过 BLOCKER 反事实门槛，并满足以下一种或多种情况：

- 存在经过反事实门槛确认的 `BLOCKER`；
- 核心用户、场景、问题或任务无法确定；
- 核心问题无真实证据；
- 核心功能完全无法追溯；
- 高风险冲突发生在问题存在性层并可能推翻方向；
- 无法定义任何能产生有效学习的原型验证目标；
- 继续探索会造成不可逆风险，或团队准备直接进入高成本实现/正式发布。

#### 方案收敛状态（补充状态，不替代原型探索状态）

##### `NO_PROPOSED_SOLUTION`

当前没有需要审计的既定方案。

##### `PROCEED_AS_HYPOTHESIS`

当前方案可以作为一个待验证选项进入低成本原型，但不得写成研究已支持的唯一方案。

##### `SUPPORTED_WITHIN_SCOPE`

当前方案在明确用户、场景和范围内有足够依据，可以进入限定原型验证。

##### `PAUSE_PROPOSED_SOLUTION`

暂停当前既定方案的收敛或高成本细化，但继续探索替代方案。典型情况：证据支持问题存在，却不支持当前默认值、功能形态、流程归属或统一策略。

强制一致性规则：

- `PAUSE_PROPOSED_SOLUTION` 可以与 `EXPLORE_WITH_GUARDRAILS` 同时出现；
- 暂停一个方案不得自动映射为 `PAUSE_CORE_PROTOTYPING`；
- 如果报告允许多方案、低成本、可逆原型，原型探索状态不得为 `PAUSE_CORE_PROTOTYPING`；
- “缺少目标产品一手研究”本身不能自动触发 `NOT_READY`，还要判断现有证据能否支持方向性探索。

#### 维度 B：研究主张就绪状态

##### `CLAIM_READY`

可以把限定范围内的核心主张表述为研究支持。

条件：

- 无未解决 `BLOCKER`；
- 核心主张均有可追溯证据；
- 关键反例、限制与适用范围已说明；
- 不将方案有效性、普遍性或长期效果超出证据范围表述；
- 核心功能需求与具体交互方案已明确区分。

##### `CLAIM_READY_AFTER_FIXES`

方向可以保留，但对外表述前需要修正证据链、限定范围或补充验证。

##### `CLAIM_NOT_READY`

不得把当前核心主张写成已验证事实。只能表述为观察、方向性模式或待验证假设。

#### 三档总评

##### `READY`

- 原型探索状态为 `EXPLORE`；
- 研究主张状态为 `CLAIM_READY`；
- 九项最低分析包不存在核心断裂。

##### `READY_AFTER_FIXES`

- 原型探索状态为 `EXPLORE` 或 `EXPLORE_WITH_GUARDRAILS`；
- 方案收敛状态可以为 `PROCEED_AS_HYPOTHESIS` 或 `PAUSE_PROPOSED_SOLUTION`；
- 研究主张状态为 `CLAIM_READY_AFTER_FIXES`，或为 `CLAIM_NOT_READY` 但团队明确只将相关内容作为假设而非已验证结论；
- 修复项、验证目标和复审条件明确；
- 不进入高成本实现承诺，不对外夸大研究主张。

##### `NOT_READY`

满足任一情况：

- 原型探索状态为 `PAUSE_CORE_PROTOTYPING`；
- 研究主张状态为 `CLAIM_NOT_READY`，且用户准备将其作为已验证结论、高成本实现或正式发布依据；
- 关键缺口没有明确处理路径；
- 团队拒绝保留不确定性或拒绝设置验证条件。

#### Issue 数量解释规则

- 经过反事实门槛确认的 `BLOCKER` 数量大于 0：通常为 `NOT_READY`。
- `MAJOR` 的数量本身不直接决定结论；必须判断其是否影响核心问题、是否可通过原型学习、是否已有防护条件。
- 多个 `MAJOR` 可以允许 `EXPLORE_WITH_GUARDRAILS`，但通常不能直接获得 `CLAIM_READY`。同一根因不得因影响多个最低分析包维度而重复计数。
- 九项最低分析包全部为 `PARTIAL` 时，必须逐项判断是否存在核心链路断裂；不得因“没有 BLOCKING_GAP”自动判为 `READY`；同时检查是否存在一个或多个 `MAJOR_GAP` 共同造成核心链路不稳定。

### 11. 生成行动计划

按优先级输出：

1. 必须先解决的 `BLOCKER`；
2. 进入原型前应解决的 `MAJOR`；
3. 可在原型阶段处理的 `MINOR`。

每个行动项包含：

- 对应 Issue ID；
- 目标；
- 推荐方法；
- 具体步骤；
- 所需材料；
- 设计师确认点；
- AI 初稿时间；
- 设计师审核时间；
- 分析执行时间；
- 如涉及招募、排期或等待，单独标记日历时间；
- 完成标准；
- 复审范围。

时间只作为参考，不作为强制期限。每个行动项必须优先输出具体范围：

- `ai_draft_time`：AI 生成初稿所需时间，仅作工具成本记录；
- `designer_review_time`：设计师审核与修正时间，例如 30–60 分钟；
- `analysis_execution_time`：实际整理、编码、分析或测试执行时间，例如 2–4 小时；
- `calendar_dependency`：招募、排期、等待数据或纵向观察，例如 2–5 个自然日。

可以附加 `effort_band` 作为摘要，但不得只写 `LOW`、`MEDIUM` 或 `HIGH`。不得把 AI 生成时间误写成完整研究耗时。

### 12. 保存审计记录

必须保留：

- 项目模式与输入版本；
- 材料索引；
- 原始审计输出；
- Issue ID 与严重程度；
- AI 生成的分析初稿；
- 设计师确认、修改与否定；
- 审计结论；
- 执行耗时；
- 复审结果；
- Skill 版本。

模板见 [输出模板](references/output-templates.md)。

## 输出模式与固定顺序

### `compact`（默认）

适用于日常项目判断、快速复审和作品集过程记录。按以下顺序输出：

1. 审计摘要；
2. 原型探索状态、方案收敛状态、研究主张状态和三档总评；
3. 3–6 个根因 Issue 注册表；
4. 关键证据边界与受影响维度；
5. `DESIGNER_DECISION_REQUIRED`；
6. 优先行动计划与复审条件；
7. Issue 统计一致性检查。

### `full`

用户明确要求完整报告、项目涉及高风险决策或需要正式归档时使用：

1. 审计摘要；
2. 项目与输入概况；
3. 材料盘点；
4. 九项最低分析包评分；
5. 根因注册表与冲突层级；
6. 证据链摘要；
7. Issue 注册表与 Issue 列表；
8. 建议补充的分析或研究；
9. 需要设计师确认的内容；
10. 原型探索状态；
11. 方案收敛状态；
12. 研究主张就绪状态；
13. 三档总评；
14. 分阶段行动计划；
15. 复审条件；
16. 审计记录信息。

不得以长篇自然语言代替结构化结果。默认不要重复描述同一根因。

## 最终质量检查

提交结果前，逐项检查：

- 是否引用了真实证据编号；
- 是否把事实、分析、决策和假设分开；
- 是否把用户建议误当成需求；
- 是否因缺少固定 UX 文档而错误判定；
- 是否解释了方法选择原因；
- 是否明确哪些内容由 AI 推断；
- 是否设置设计师确认节点；
- 是否存在编造用户事实；
- 是否先识别根因和冲突层级，再判断严重程度；
- 九项最低分析包是否被错误地逐项自动转成 Issue；
- 候选 BLOCKER 是否通过反事实门槛；
- 暂停当前方案是否被错误扩大为暂停整个问题方向；
- Issue 严重程度是否与设计风险匹配；
- Issue ID 是否唯一，行动计划是否只引用已存在的 Issue；
- `BLOCKER`、`MAJOR`、`MINOR` 与总 Issue 数是否由 Issue 注册表派生；
- 审计摘要、Issue 列表、三档总评和审计记录中的 Issue 统计是否完全一致；
- 每个未关闭的 `BLOCKER` 和 `MAJOR` 是否都有行动项、设计师确认点或明确复审条件；
- 原型探索状态、方案收敛状态与研究主张状态是否分别判断；
- 如果允许低成本、多路径、可逆探索，是否错误输出 `PAUSE_CORE_PROTOTYPING`；
- 三档总评是否与两个维度和 Issue 风险一致；
- 是否仅因 Issue 数量机械下结论；
- 是否越界替设计师决定功能层级、流程或最终方案；
- 是否正确解释小样本只支持探索而不支持普遍性；
- 原型验证计划完整度、执行状态和结果证据是否分别记录；
- 行动计划是否给出具体时间范围，而非只给抽象等级；
- 涉及具体方案的建议是否提供多个选项而非唯一答案；
- 行动计划是否可执行；
- 是否保留设计师最终控制权。
